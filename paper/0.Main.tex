\begin{abstract}
\textbf{Problem.} Quantum supremacy is often discussed as if faster quantum hardware will solve many practical problems automatically. This is not enough for HPC users. The real question is when a quantum-circuit application can beat a native HPC application on the same real task and at the same quality.

\textbf{Approach.} This paper presents a quantum supremacy modeling and analysis methodology. \SystemName runs native baselines and quantum-circuit versions of the same workload with shared inputs and quality targets. It then uses the measured circuit cost to model the supremacy threshold, i.e., the quantum hardware speed needed to beat the native path.

\textbf{Result.} On \Perlmutter, our first expanded workload sweep runs 160 \texttt{sklearn digits} cases across class pairs, sample counts, PCA dimensions, depths, and seeds. Quantum kernels require a median 421.9$\times$ simulation-to-native speedup to match the native path; QNN/VQC requires 64.9$\times$ but usually misses native quality. We then run a 3,552-case practical suite across ML, chemistry, optimization, and simulation on up to 32 GPU nodes. Median required speedups range from 3,071.0$\times$ for Hamiltonian simulation to 287,045.6$\times$ for optimization. Baseline-coverage gates add sparse Krylov simulation baselines and a 104-case OpenFermion/PySCF chemistry sweep with LiH/H$_2$O active-space fixtures up to 8 qubits. These results do not claim quantum wins today. They show why practical quantum supremacy must be modeled as a workload-specific threshold.
\end{abstract}
