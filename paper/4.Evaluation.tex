\section{Evaluation}

This section reports the first measured \SystemName result and then defines the remaining evaluation needed for practical application coverage. The current result is not a claim that quantum wins today. It is a calibration experiment that shows how \SystemName converts an application comparison into a supremacy threshold.

\subsection{Evaluation Setup}

Experiments run on NERSC \Perlmutter. Login-node smoke tests validate correctness, while performance experiments run through Slurm. The first expanded sweep uses \texttt{gpu\_shared} jobs with one A100 GPU per job. Each job records JSON outputs, Slurm metadata, elapsed time, and allocation information.

\noindent\textbf{Key result.}
The first result supports the main thesis: the useful output is not ``quantum is faster'' or ``quantum is slower.'' The useful output is the hardware requirement. For this workload, even when quantum kernels achieve good accuracy, the projected execution must improve by a median 421.9$\times$ to reach native time. For QNN/VQC, the median threshold is 64.9$\times$, but the model usually fails to match native accuracy.

\subsection{Quality Sensitivity}

Table~\ref{tab:class-sensitivity} shows that the threshold depends on the data pair. The easy pair, 0-vs-1, gives high quantum-kernel accuracy. Harder pairs such as 3-vs-8 and 5-vs-8 reduce quality and make a simple speedup claim invalid. This is exactly why \SystemName keeps quality and runtime together.

\subsection{Allocation and Slurm Cost}

The expanded sweep used eight completed shared-GPU chunks. The total measured GPU time is 0.4089 GPU-hours, and the Slurm billing sum is 13.0844 core-hours. All stderr logs are empty. Several pending jobs were cancelled before allocation while we adjusted the queue strategy; they have zero elapsed time and do not contribute to the accounting.

\subsection{Why Digits Is Not Enough}

The digits workload is useful because it is controlled, cheap, and easy to repeat. It is not enough for a practical quantum supremacy claim. Real users care about broader applications: AI pipelines, molecular energy estimation for drug discovery, optimization, and scientific simulation. These workloads have different native baselines and different quantum overheads.

\subsection{Required Practical Workloads}

Before submission, \SystemName must add practical workloads beyond digits:

\begin{itemize}[leftmargin=*]
    \item \textbf{ML workloads.} Add multiclass classification and larger tabular/image datasets with native logistic, MLP, tree/SVM, and GPU neural baselines.
    \item \textbf{Drug discovery and chemistry.} Add a molecular energy workload with a native chemistry or surrogate baseline and a VQE-style quantum circuit path.
    \item \textbf{Optimization.} Add QAOA-style MaxCut, portfolio, or scheduling instances with native heuristic and solver baselines.
    \item \textbf{Scientific simulation.} Add Hamiltonian simulation or quantum dynamics workloads with native numerical solver baselines.
\end{itemize}

\subsection{Hardware Projection}

The current projection uses measured circuit metadata to compute a required speedup relative to native runtime. The next version should convert this speedup into logical gate time, measurement time, shot throughput, and error-correction overhead. The output should be a heatmap that answers: for each workload family, how fast must quantum hardware be before the quantum path beats the native HPC path at the same quality?

\subsection{Sensitivity and Stability}

The current expanded sweep covers class pair, sample count, PCA dimension, circuit depth, and seed. The next experiments must add warmup separation, repeated trials, shot sensitivity, ansatz sensitivity, optimizer sensitivity, and error mitigation overhead. These are necessary because small circuit experiments can be dominated by initialization, Python dispatch, and circuit construction overhead.
