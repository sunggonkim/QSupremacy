\section{Evaluation}

This section follows the evaluation style of our previous systems papers: setup first, then the representative result, scale-out evidence, workload-specific detail, component diagnosis, architecture projection, backend ablation, and stability. The result is not a claim that quantum wins today. The result is a measured architecture model that shows how far each quantum-circuit application path is from its native HPC counterpart and which future-system resource must improve.

\subsection{Evaluation Setup}

Experiments run on a \LeadershipSystem. Login-node smoke tests validate correctness, while performance experiments run through Slurm on GPU nodes with four NVIDIA A100 GPUs per node. The unit of comparison is a same-input application case: \SystemName measures a native HPC/ML path, measures a quantum-circuit application path on the simulator, records quality for both paths, and reports $T_{\mathrm{qsim}}/T_{\mathrm{native}}$ only when the quality target is interpretable. The native path is never another quantum simulator.

The completed campaign contains a 160-case controlled ML calibration, a 3,552-case practical suite, 116-case and 104-case molecule/HamSim coverage gates, weak and fixed-work scaling from 1 to 256 GPUs, a 7,104-case larger-workload gate on 256 GPUs, and 12 warmup-separated repeat trials. \subsection{Workload-Level Thresholds}

The main result starts at the workload level because practical advantage is not a simulator-versus-simulator comparison. The large practical suite covers ML classification, molecular energy estimation, MaxCut optimization, and Hamiltonian simulation. Each row compares a native HPC/ML implementation with a quantum-circuit application path under the same input and quality metric.

Figure~\ref{fig:practical-suite} shows the representative application-level threshold landscape beyond the controlled digits sweep. The main practical-suite result uses the 3,552-case profile on 128 GPUs. ML selects among six native classifiers, MaxCut selects among exact, greedy, local-search, and annealing baselines, molecule uses dense exact and sparse Lanczos candidates, and HamSim uses dense exact and sparse Krylov candidates. The quantum paths are executed through the \cuQuantum/cuStateVec application pipeline.

As shown in Figure~\ref{fig:practical-suite}, native execution remains extremely fast: the median native path is 2.09 ms for ML, 0.170 ms for molecule, 0.024 ms for MaxCut, and 2.08 ms for HamSim. The simulated quantum-circuit path is roughly seven seconds per case. This creates median required speedups of 3,726.4$\times$ for ML, 42,491.4$\times$ for molecule, 287,045.6$\times$ for MaxCut, and 3,071.0$\times$ for HamSim. These numbers are not a final hardware claim; they are the measured input to the projection model.

The threshold spread is caused by two forces: the native side often finishes in microseconds to milliseconds, while the quantum-circuit path pays the application cost of encoding, repeated circuit evaluations, state-vector simulation, measurement extraction, and quality scoring. HamSim has the smallest median runtime threshold, molecule has a larger but often speed-dominated threshold, and MaxCut has the largest threshold because the native path is extremely fast while the current QAOA path also carries a quality gap. ML is split: some circuit paths have moderate runtime thresholds, but advantage still depends on closing the quality gap.

\begin{observationbox}
\textbf{Observation 1:} The practical-suite gap is workload-specific. Native paths often finish in microseconds to milliseconds, while the simulated quantum-circuit path takes about seven seconds per case. The architecture question is therefore not whether the simulator is slow; it is whether future quantum systems should buy speed, quality recovery, shot parallelism, or lower control overhead for each workload family.
\end{observationbox}

\subsection{Workload Deep Dives}

The workload-level result is the representative picture. This subsection gives the workload-specific evidence behind that picture, in the same style as ScaleQsim's diverse-circuit analysis: each workload is treated as a separate case with its own baseline boundary and interpretation.

\subsubsection{Controlled ML: scikit/QKernel and scikit/QNN}

The controlled benchmark is the expanded \texttt{sklearn digits} sweep. It varies class pair, sample count, PCA dimension, circuit depth, and seed. The digits circuits use one qubit per PCA feature dimension, so the controlled sweep uses 4, 8, 12, and 16 qubits.

The native path is the fastest valid classifier among softmax regression, MLP, linear ridge, RBF kernel ridge, kNN, and nearest centroid on the same PCA features and split. QKernel maps the same features into a quantum feature map, simulates the circuit evaluations needed to build a kernel matrix, and passes that matrix to a classical classifier. QNN/VQC maps the same features into a parameterized circuit and updates trainable parameters through a classical optimizer.

Figure~\ref{fig:digits-results} shows the controlled ML result with both axes required for an advantage claim: runtime threshold and quantum-model quality.

\subsubsection{Molecule and HamSim Coverage}

We run a separate accept-profile gate to strengthen the two application families that are easiest to criticize as toy baselines: molecular energy estimation and Hamiltonian simulation. The molecule gate includes OpenFermion and PySCF-generated H$_2$, LiH, and H$_2$O active-space Hamiltonians, in addition to the built-in minimal H$_2$ and molecular-chain surrogate. The HamSim gate compares dense exact evolution with sparse Krylov evolution on TFIM and Heisenberg Hamiltonians from 4 to 8 qubits.

The strengthened molecule and HamSim baselines execute correctly in the same bundled one-node run. The job completed 116 cases in 6 minutes and 5 seconds with exit code 0:0; each of the four A100 tasks completed 29 cases, and stderr logs were empty. Molecule reports a median 63,566.8$\times$ required speedup over 56 cases, and HamSim reports 4,185.2$\times$ over 60 cases.

The stronger native side changes the interpretation because it prevents the quantum path from being compared against a single dense toy solver. For molecule, both dense exact and sparse Lanczos/eigensolver candidates are evaluated for every case. For HamSim, sparse Krylov becomes the selected native method in 34 of 60 cases, especially at 6--8 qubits.

\noindent\emph{H$_2$, LiH, and H$_2$O active-space gate.}
We then run the expanded molecule-only accept profile with the 4--8 qubit OpenFermion and PySCF fixture set. The molecular integrals and Jordan-Wigner Hamiltonians are generated once into JSON fixtures before the timed application comparison; each timed case starts from the same stored Pauli Hamiltonian for both native and quantum paths.

Job 55515248 completed 104 molecule cases on one GPU node in 5 minutes and 23 seconds with exit code 0:0, 104 raw JSON outputs, and empty stderr. The larger active-space subset includes LiH and H$_2$O at 6 and 8 qubits. LiH active-space cases require 21,847.9$\times$ at 6 qubits and 821.5$\times$ at 8 qubits; H$_2$O requires 21,613.0$\times$ at 6 qubits and 788.0$\times$ at 8 qubits.

Dense exact remains the selected runtime baseline because these fixtures are still small, but sparse Lanczos is the best-quality native method in 62 of 104 cases. This result keeps the comparison honest: the molecule path is no longer only H$_2$, but the native side still reflects the problem size actually executable by the quantum-circuit path.

\subsubsection{MaxCut-QAOA}

MaxCut is the hardest practical family in the current suite. The native side selects among exact enumeration, greedy assignment, local search, and simulated annealing, while the quantum path uses a QAOA-style circuit.

In the strong-native run, the selected optimization baselines are mostly greedy assignment, with exact enumeration selected when it is fastest at the best cut value. The large practical suite reports a median 287,045.6$\times$ required speedup for MaxCut.

This number is high because the native path is extremely fast and the current QAOA grid has a large objective gap. MaxCut therefore behaves like a quality-first workload before faster quantum execution can matter.

\subsection{Design Projection: How Much Improvement Is Enough?}

Section~IV-E gives the location of the bottleneck; this subsection gives the required amount of improvement. The practical-suite result gives one speed threshold per case, but a speed-only threshold is incomplete. A practical advantage claim also needs comparable output quality, enough shot/evaluation throughput, and a control stack that does not reintroduce a serial floor. We therefore convert each measured case into an advantage frontier over projected quantum execution speedup and quality-gap recovery, then instantiate the same records under a concrete shot/control sensitivity model.
Figure~\ref{fig:advantage-frontier} shows the primary frontier at 90\% quality-gap recovery.

\begin{figure}[t]
\centering
\includegraphics[width=0.96\linewidth]{figures/advantage_frontier.pdf}
\Description{Line plot showing fraction of cases entering the projected advantage region at 90 percent quality-gap recovery as projected speedup changes.}
\caption{Advantage frontier at 90\% quality-gap recovery. The curves show the fraction of measured cases in each workload family that would enter the advantage region as projected quantum execution speedup improves. The secondary axis maps representative speedups to effective quantum execution time using the measured seven-second circuit path.}
\label{fig:advantage-frontier}
\end{figure}

For a projected quantum speedup $S$ and quality-gap recovery $R$, a case enters the advantage region only if
\[
S \geq \frac{T_{qsim}}{T_{native}}
\quad\text{and}\quad
(1-R)\Delta Q \leq \epsilon_w ,
\]
where $\Delta Q$ is the measured quality gap in the workload's natural units and $\epsilon_w$ is the workload tolerance. The recovery parameter $R$ is not a measured error-mitigation result; it is a requirement axis.

As shown in Figure~\ref{fig:advantage-frontier}, HamSim is the closest family: with 90\% quality-gap recovery, a $10^4\times$ projected execution improvement covers 54.9\% of measured HamSim cases. Molecule needs a larger runtime shift: at the same recovery level, $10^5\times$ covers 57.1\% of molecule cases. ML shows the opposite behavior. A $10^5\times$ speed improvement covers only 9.8\% of ML cases at 90\% recovery, but almost all cases if the quality gap is fully closed. MaxCut is the hardest family in the current suite; even $10^6\times$ speedup covers only 22.9\% of cases at 90\% recovery and requires full quality recovery to cover all cases.

The frontier should be read as an architecture target sheet rather than a simulator score. HamSim points first to logical-operation latency, measurement latency, and shot scheduling. Molecule needs those speed levers plus energy-quality recovery. ML and MaxCut require algorithmic-quality recovery before a gate-speed investment can translate into application advantage. The FT-stack sensitivity below then asks whether shot parallelism and decoder/control overhead let the speed target survive in a concrete system model.

\caption{Tolerance sensitivity of the advantage frontier. The same measured cases can be reinterpreted under stricter or looser quality budgets; this changes quality-limited ML and MaxCut much more than speed-bound molecule.}

As shown in Figure~\ref{fig:tolerance-sensitivity}, at 90\% recovery, HamSim at $10^4\times$ moves from 46.9\% to 54.9\% to 68.9\% as the tolerance changes from 0.5$\times$ to 1$\times$ to 2$\times$. ML at $10^5\times$ is much more tolerance-sensitive, moving from 0.8\% to 9.8\% to 83.8\%. Molecule at $10^5\times$ is speed-bound under these tolerances, staying at 57.1\% until the tolerance becomes very loose.

Relaxing the tolerance helps only when quality is the active bottleneck. ML changes sharply because many cases are close to the runtime target but fail the quality gate. Molecule changes little because many cases are still runtime-bound. MaxCut remains hard unless both the speedup and quality budget are relaxed.

Figure~\ref{fig:ft-shot-sensitivity} instantiates the symbolic projection terms for a concrete subset-style check using every practical-suite case. The sensitivity uses the measured gate/evaluation metadata with an illustrative surface-code lower-bound stack: $d=25$, $\tau_c=1\,\mu$s, $k_1=1$, $k_2=4$, $k_m=1$, $5\,\mu$s decoder latency per circuit evaluation, and $50\,\mu$s of residual control/queue overhead per evaluation. Only the logical gate portion is divided by effective shot parallelism; decoder/control overhead remains serial in this lower-bound model.

As shown in Figure~\ref{fig:ft-shot-sensitivity}, runtime falls as effective shot parallelism increases, but the serial decoder/control floor prevents unbounded improvement. The speed axis is dimensionless, but it has a physical interpretation: since the measured circuit path is about seven seconds per case, $10^4\times$, $10^5\times$, and $10^6\times$ correspond to roughly 0.7 ms, 70 $\mu$s, and 7 $\mu$s of effective end-to-end quantum execution per measured case before residual host and error terms.

This conversion is a normalization target, not a claim that gate speed alone reaches the target. A fault-tolerant instantiation reaches that budget only if logical cycle time, code distance, decoder bandwidth, magic-state throughput, controller scheduling, and effective shot parallelism jointly satisfy the decomposed model in Section~III. The model therefore exposes when increasing $P_{\mathrm{shots}}$ stops helping.

\begin{observationbox}
\textbf{Observation 5:} The frontier converts measurements into design guidance. Faster logical operations and shot-level parallelism are most valuable for HamSim and part of molecule, but the FT-stack sensitivity shows that decoder/control overhead and finite evaluation parallelism create a floor. For ML and MaxCut, faster gates alone do not create advantage until quality and hybrid-loop overhead improve.
\end{observationbox}

\subsection{Backend and Stability Gates}

The production records use the \cuQuantum/cuStateVec application pipeline so that every practical-suite case shares the same native path, quantum-circuit logic, simulator interface, and Slurm accounting path. A small backend-diversity gate confirms that other Perlmutter stacks are callable on sanity circuits: \cuQuantum/cuStateVec passes in 3.18 s, qsim CPU in 4.50 s, qsim GPU in 0.55 s, CUDA-Q cuStateVec in 6.02 s, and Qiskit Aer CPU in 1.23 s; Qiskit Aer GPU is unsupported in the current device stack. This is not used as a performance ranking because the full application path includes encoding, repeated evaluations, optimizer/classifier logic, state extraction, quality scoring, and Slurm-recorded execution. The official sweep is also validated with bundled Slurm runs: one \texttt{salloc}/\texttt{srun} pilot completed in 6 minutes 54 seconds with 96 raw JSON outputs and empty stderr, and job 55516885 completed 12 warmup-separated trials in 58 seconds with exit code 0:0; the maximum quantum-runtime CV is 0.0400.
