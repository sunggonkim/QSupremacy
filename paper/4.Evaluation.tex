\section{Evaluation}

This section follows the evaluation style of our previous systems papers: setup first, then the representative result, scale-out evidence, workload-specific quality analysis, component diagnosis, and architecture projection. The result is not a claim that quantum wins today. The result is a measured architecture model that shows how far each quantum-circuit application path is from its native HPC counterpart and which future-system resource must improve.

\subsection{Evaluation Setup}

\noindent\textbf{Hardware Specification.}
Experiments run on a \LeadershipSystem. Login-node smoke tests validate correctness, while performance experiments run through Slurm on GPU nodes with four NVIDIA A100 GPUs per node.

\noindent\textbf{Benchmark.}
The unit of comparison is a same-input application case: \SystemName measures a native HPC/ML path, measures a quantum-circuit application path on the simulator, records quality for both paths, and reports $T_{\mathrm{qsim}}/T_{\mathrm{native}}$ only when the quality target is interpretable. The completed campaign contains a 160-case controlled ML calibration, a 3,552-case practical suite, 116-case and 104-case Chem/Sim. coverage gates, weak scaling through 7,104 cases on 256 GPUs, fixed-work 7,104-case scaling from 64 to 256 GPUs, a four-workload larger stress gate, and 12 warmup-separated repeat trials.

\noindent\textbf{Baselines.}
A case is one concrete input/configuration tuple, such as an ML class pair and circuit depth, a molecule and ansatz, a graph and QAOA setting, or a Hamiltonian and Trotter setting. The native path is never another quantum simulator; it is the fastest valid non-quantum candidate implemented for the same input and quality metric.

\noindent\textbf{Feasibility.}
The suite is intentionally exact-instrumented and small enough for state-vector execution. This scope favors strong native baselines and does not claim deployment-scale advantage; it gives a controlled lower-level record for architecture modeling. To check that the record path is not limited to the smallest knobs, a one-node stress gate completed four larger/deeper cases: 512-sample 12-feature ML at depth 3, H$_2$O active-space Chem with an 8-qubit layer-3 VQE grid, 20-node MaxCut QAOA, and 12-qubit 16-step Heisenberg simulation. These stress cases are not folded into the practical-suite medians; they verify that the same-input logging path extends beyond the main exact sweep. The measured threshold plots use $T_{\mathrm{qsim}}/T_{\mathrm{native}}$, where \cuQuantum executes the full quantum-circuit application path today. The projection plots use $T_{\mathrm{qhw}}/T_{\mathrm{native}}$, where recorded gates, measurements, shots, repeated evaluations, and quality gaps are priced by the Section~III future-hardware model. These axes answer different questions and should not be interchanged.

\subsection{Workload-Level Thresholds}

To evaluate application-level measured thresholds, each point compares a quantum-circuit path with the selected native HPC/ML implementation on the same input and quality metric. This is not simulator-versus-simulator: the native side is the non-quantum path for the same case. Figure~\ref{fig:practical-suite} shows the 3,552-case practical suite on 128 GPUs. The x-axis is the measured speedup that would be needed to replace today's \cuQuantum application path with a future execution path at native time, the y-axis is quality gap to native, and outlined points show workload medians. Native paths finish in microseconds to milliseconds, while the simulated quantum-circuit paths take seconds per case; across all cases, the mean required speedup is 79,291$\times$ and the median is 15,164$\times$.

\noindent\textbf{ML.} The selected native baseline is a classical classifier on the same feature vector and split: scikit-learn candidates in the main sweep, plus a separate PyTorch AMP/XGBoost production-native gate. The quantum side uses two \cuQuantum-executed formulations. QKernel spends work on many pairwise feature-map circuits to build a kernel matrix, while QNN/VQC spends work on repeated parameterized-circuit evaluations during training. A QPU would make the circuit evaluations physical rather than simulated, but it would not remove feature loading, shots, kernel-matrix repetition, or optimizer feedback. This is why the ML points mix runtime pressure with a visible quality gap.

\noindent\textbf{Chem.} The native baseline starts from the same active-space molecular Hamiltonian as the quantum path. Dense exact builds the full Hamiltonian matrix and diagonalizes it; sparse Lanczos applies the Hamiltonian iteratively to estimate the lowest energy without storing the full dense matrix. These native solvers are strong at the small qubit counts that the circuit path can still execute, because they return deterministic energies without shots. The quantum formulation is VQE: prepare an ansatz state, measure Pauli terms, and aggregate an energy estimate. A QPU can represent the molecular state physically, but the measured cases still pay two-qubit gates, many term measurements, and energy-accuracy recovery.

\noindent\textbf{Opt.} The optimization family is instantiated with MaxCut graphs in this suite. The native baseline treats each graph as a classical combinatorial optimization problem: exact search enumerates candidate bitstrings when the graph is small, while greedy, local-search, and simulated-annealing candidates cheaply improve cuts by flipping or accepting bit assignments. These methods are fast here because each objective evaluation is a simple edge-count calculation. The quantum formulation is QAOA: edge weights become phase-separation gates, mixer gates explore bitstrings, and repeated sampling estimates the objective value. A QPU could sample from the QAOA state without state-vector simulation, but it still needs enough circuit depth and parameter quality to beat cheap native heuristics.

\noindent\textbf{Sim.} The scientific-simulation family is instantiated with Hamiltonian time evolution. The native baseline stores the quantum state as a classical complex vector and evolves it with the Hamiltonian. Dense exact methods materialize the small Hamiltonian/evolution operator, while sparse Krylov methods use repeated Hamiltonian-vector products in a low-dimensional Krylov subspace. The quantum formulation is Trotterized Hamiltonian simulation, where the same local Hamiltonian terms become a sequence of unitary gates. This is the most hardware-aligned mapping in the suite: a QPU directly applies unitary evolution instead of explicitly storing the whole state vector. Therefore Sim. has the lowest median threshold, although Trotter depth, measurements, and quality recovery still determine whether faster gates become useful.

\begin{observationbox}
\textbf{Observation 1:} The practical-suite gap is workload-specific. Native paths often finish in microseconds to milliseconds, while the simulated quantum-circuit path takes about seven seconds per case. The architecture question is therefore not whether the simulator is slow; it is whether future quantum systems should buy speed, quality recovery, shot parallelism, or lower control overhead for each workload family.
\end{observationbox}

\subsection{Scaling Evidence and QPU Architecture Targets}

This subsection uses Perlmutter scaling to separate parallel work from serial overhead. The large-profile suite contains independent same-input application cases, so weak scaling asks whether more GPUs can process more circuit-application cases, while strong scaling asks when a fixed evidence set runs out of useful parallel granularity. The result is not a claim that QPUs scale like GPUs. It identifies which kind of parallelism matters for a future QPU: batched circuits, batched shots, repeated evaluations, and low-latency control, rather than simply adding devices.

For a QPU, the corresponding scaling axis is not ``more devices'' alone; it is whether circuits, shots, and hybrid evaluations can be batched enough to amortize measurement, control, and feedback latency.
\end{observationbox}

\subsection{Application Quality Beyond Runtime}

The workload-level landscape in Section~IV-B reports runtime thresholds, but runtime alone is not quantum advantage. The \cuQuantum/cuStateVec path is a state-vector execution of the chosen circuit application; the production suite does not inject a NISQ noise model. The quality gaps below are therefore application-quality gaps caused by feature encodings, ansatz/search limits, approximation order, optimizer behavior, and native-baseline strength.

\noindent\textbf{ML model quality.}
Figure~\ref{fig:digits-results} shows the expanded \texttt{sklearn digits} calibration. The native path selects the fastest valid classifier on the same PCA features and split. QKernel maps those features into a quantum feature map and builds a kernel matrix from many circuit evaluations; QNN/VQC trains a parameterized circuit through a classical optimizer. This setup isolates an architecture-relevant issue: even with noiseless state-vector execution, the quantum model can miss native accuracy because the encoding or trainable circuit does not match the native model class.

This is why \SystemName models advantage as a speed-quality frontier rather than a simulator-runtime ratio.

\noindent\textbf{Architecture pressure map.}
Figure~\ref{fig:advantage-frontier} converts the runtime gap and time location into an actionability map. It does not ask for one scalar QPU speedup. It exposes which column first becomes architectural pressure: quality recovery, hybrid-loop count, decode/control latency, two-qubit execution, or the total projected runtime relative to native. The figure is not a current-hardware benchmark. Public fault-tolerance demonstrations have reached below-threshold logical memory and real-time decoding at small code distance, while industrial roadmaps still place large fault-tolerant machines later this decade~\cite{googleqec2025belowthreshold,ibmftqcroadmap2025}. Thus the plotted targets should be read as lower-bound design pressure under the optimistic Section~III stack, not as claims that an existing QPU, annealer, or cloud backend can execute these circuits at the shown rates.
For projected quantum time $T_{\mathrm{qhw}}$ and quality-gap recovery $R$, a case enters the advantage region only if
\[
T_{\mathrm{qhw}} < T_{\mathrm{native}}
\quad\text{and}\quad
(1-R)\Delta Q \leq \epsilon_w ,
\]
where $\Delta Q$ is the measured quality gap in the workload's natural units and $\epsilon_w$ is the workload tolerance. The recovery parameter $R$ is not a measured error-mitigation result; it is a requirement axis. The map shows why the target is architectural rather than a generic gate-speed claim. ML has high required recovery and high hybrid count, so useful hardware needs batched circuit submission and low-latency feedback only after the representation improves. Chem has lower hybrid count but the largest decode/control share, making near-QPU decoding, measurement aggregation, and observable batching first-order. Opt. combines high recovery, many hybrid evaluations, and nontrivial two-qubit pressure, so speed alone cannot compensate for a shallow search landscape. Sim. has low hybrid count and a low total runtime ratio under the optimistic model, but its pressure moves to two-qubit execution and Trotter/observable quality. Quantum annealing is relevant mainly to optimization problems that can be embedded as energy minimization or sampling problems~\cite{dwaveannealingdocs}; it is not a drop-in replacement for QNN/QKernel, VQE chemistry, or Trotterized Hamiltonian simulation in this suite.

\begin{observationbox}
\textbf{Observation 4:} Architecture targets require amount, location, and actionability. Figure~\ref{fig:advantage-frontier-total} shows whether runtime is a barrier, Figure~\ref{fig:architecture-demand-time-share} shows where projected time is spent, and Figure~\ref{fig:advantage-frontier} maps the dominant design pressure. The useful accelerator is workload-specific: representation plus hybrid-loop co-design for ML and Opt., decoder/control acceleration for Chem, and Hamiltonian-simulation-oriented execution for Sim.; annealing is only a candidate for the optimization subset, not a general substitute for the gate-model paths.
\end{observationbox}

\subsection{Sensitivity and Design Frontier}

Runtime parity is necessary but not sufficient for quantum advantage. A QPU can beat native time and still lose if output quality misses the application tolerance; conversely, a quality-correct circuit can remain unusable if the FT stack leaves a serial decoder/control floor. Quality recovery is not modeled as a free physical process. For ML it may require different encodings, larger kernels, or deeper trainable circuits; for Chem it may require richer ansatz families, more Pauli measurements, or better energy estimators; for Opt. it may require deeper QAOA/search; and for Sim. it may require higher Trotter order or better observable estimation. Each mechanism can change both $\Delta Q$ and runtime. Figure~\ref{fig:sensitivity-maps} therefore checks the two assumptions behind Figures~\ref{fig:architecture-demand-time} and~\ref{fig:advantage-frontier}: application quality recovery and hardware-stack scaling.

Figure~\ref{fig:tolerance-sensitivity} isolates the application side of the frontier. It uses the measured speedup requirements and quality gaps, then reports selected cuts through projected execution speedup and quality-gap recovery without rerunning GPU jobs. This view makes the quality gate explicit: at 90\% recovery, Sim. reaches 55\% of cases at $10^4\times$ and 72\% at $10^5\times$, Chem reaches 57\% at $10^5\times$, and Opt. remains at 23\% even at $10^6\times$ unless recovery is essentially complete. ML reaches almost all cases only near full recovery, while Sim. is the first workload family to expose useful coverage before perfect recovery.
The nonzero entries on the left of Figure~\ref{fig:tolerance-sensitivity} are not current-hardware wins. They are projected wins under the selected speedup and recovery cuts. Sim. opens early because its measured thresholds are lower than the other workload families and its quality gaps are often small: at $10^4\times$, 69\% of Sim. cases pass the runtime gate, 72\% pass the 90\% recovery quality gate, and 55\% pass both. ML opens only for a small subset of easy, low-gap cases: at $10^4\times$ and 90\% recovery, 64\% of ML cases pass the runtime gate but only 9.8\% pass the quality gate, leaving 7\% that pass both. Thus the early cells identify where the model is least far from advantage, not where today's QPU is already advantaged.

Figure~\ref{fig:ft-shot-sensitivity} isolates the hardware-stack side. It instantiates the symbolic projection terms using every practical-suite case, measured gate/evaluation metadata, and an offline sweep of five hardware scenarios: a conservative surface-code point with limited useful shot lanes and a larger decode/control floor, a resource-estimator-like point, the default optimistic stack from Section~III, an LDPC/future-like point with lower overhead and larger batching, and an aggressive batched upper-bound point~\cite{googleqec2025belowthreshold,webber2022impact,azureestimator,bravyi2024qldpcmemory}. The matrix separates architecture mechanisms more clearly than a timing lollipop. Conservative and resource-estimator-like assumptions erase most optimistic coverage; moving to the default stack opens Sim. and a small ML slice but leaves Chem and Opt. blocked by runtime or quality; LDPC/future-like and aggressive batched points reduce runtime for ML and Chem, yet Opt. remains quality-limited and runtime-slower. Sim. is less sensitive to these hardware levers because runtime is already below native under the optimistic projection and quality is the remaining gate.
For computer architects, the speedup source is therefore not a scalar QPU clock. The useful hardware path depends on which term the workload exposes. ML and Opt. need batched circuit submission, fast measurement/readout, low-latency classical feedback, and better quantum representations before extra shot lanes become useful. Chem is the clearest near-QPU accelerator target: VQE-style energy estimation repeats many Pauli-term evaluations, so decoder bandwidth, controller scheduling, measurement aggregation, and observable batching directly reduce the serial floor. Sim. points to a different accelerator style: a Hamiltonian-simulation-oriented analog/digital path can be runtime-attractive under this model, but its value is gated by fidelity, Trotter order, and observable quality rather than by more launch lanes. Annealing hardware can matter for optimization instances that embed cleanly as energy minimization, but Figure~\ref{fig:ft-shot-sensitivity} shows that the Opt. row still needs quality recovery and broader hybrid co-design; annealing is not a general replacement for the gate-model ML, Chem, or Sim. paths.

\FloatBarrier
\begin{observationbox}
\textbf{Observation 5:} Sensitivity separates application recovery from hardware scaling. The speed-quality map shows which workloads need better quantum representations before speed matters; the hardware map shows that conservative shot bounds remove much of the optimistic frontier. Chem is the clearest near-QPU control target, Opt. needs broader co-design, and Sim. is a runtime-ready but quality-gated accelerator candidate only under explicit future-hardware assumptions.
\end{observationbox}
