\section{Introduction}

Quantum computing is often described through broad application promises: better machine learning, faster molecular modeling, improved optimization, and natural Hamiltonian simulation. For HPC users, the important question is more concrete. A future quantum path is useful only if it beats a strong native HPC path on the same input, at the same quality, after all application overheads are included.

Current quantum hardware is not yet large and reliable enough to answer this question directly for many practical workloads. HPC systems therefore play a second role beyond accelerating quantum-circuit simulation: they are the measurement instrument for modeling when a quantum-circuit application could become competitive. The missing systems problem is to connect simulator measurements, native baselines, quality targets, and future hardware projections into one end-to-end break-even analysis.

Existing simulation systems provide the first part of this stack. Libraries such as \cuQuantum execute quantum circuits on GPUs, while prior systems such as ScaleQsim and AURORA-Q improve simulation scalability on leadership-scale systems~\cite{scaleqsim,auroraq}. These systems answer an important question: how can we simulate larger quantum circuits faster on HPC?

But simulator scalability is not the same as application-level quantum supremacy. A simulator can be faster than another simulator, but the quantum-circuit application can still be slower than a native HPC application. A native classifier can train directly on GPU-friendly tensors, while a quantum-circuit classifier must encode data, build circuits, run many evaluations, extract measurements, and run classical postprocessing. Similar gaps appear in chemistry, optimization, and scientific simulation: the quantum kernel may be promising, but the end-to-end application still includes input preparation, repeated evaluations, error overhead, and classical control. These stages can dominate total time.

\noindent\textbf{Observation 1: Simulator speed is not application speed.}
Figure~\ref{fig:intro-gap} shows the comparison target of \SystemName. A circuit simulator is only one component of the quantum path. The full quantum path also includes encoding, circuit generation, repeated evaluations, measurement, optimizer steps, and postprocessing.

\noindent\textbf{Observation 2: Native baselines matter.}
Native HPC/ML applications already use mature software stacks and efficient kernels. A fair quantum supremacy claim must therefore compare against a native implementation of the same workload, not only against another quantum simulator.

\noindent\textbf{Observation 3: Supremacy is a break-even condition.}
Even if the quantum-circuit path is slower today, it can still be useful if it tells us how fast future quantum hardware must be. Thus, the goal is not only to measure \cuQuantum time. The goal is to invert the measurement and compute the required quantum gate time, shot throughput, and error overhead.

\noindent\textbf{Observation 4: Real applications are diverse.}
Public claims about quantum computing often move from one successful example to broad expectations such as better AI, faster drug discovery, or better optimization. A systems paper cannot validate such claims with one toy workload. It must cover representative application families and show the threshold for each family.

\noindent\textbf{Observation 5: Advantage is a feasible region, not a slogan.}
For a practical workload, quantum advantage depends on several conditions being true at the same time: the quantum path must reach the target quality, the native baseline must be strong, the circuit must fit the available logical qubits, shots must be parallelized enough, and error overhead must not erase the speedup. \SystemName therefore reports an advantage frontier rather than a single yes/no answer.

Many previous studies focus on one part of this stack. Table~\ref{tab:intro-position} summarizes the gap. ScaleQsim and AURORA-Q improve quantum simulation on HPC systems. \cuQuantum provides high-performance GPU primitives. Native ML frameworks provide strong classical baselines. \SystemName connects these pieces into an application-level supremacy threshold model.

\noindent\textbf{Key idea.}
\SystemName treats quantum supremacy as a modeling and analysis problem. The supremacy threshold is the point where the projected quantum-circuit path becomes faster than the measured native HPC and ML path under the same workload and quality target. For each workload, \SystemName records the cost of each stage and then projects the quantum hardware region where this condition holds.

We present \SystemName, a quantum supremacy modeling and analysis study for HPC systems. \SystemName starts with a controlled ML workload: \texttt{sklearn digits} native ML baselines, quantum kernel classifiers, and QNN/VQC classifiers. This first workload validates the measurement pipeline. We then scale the study to a practical suite with ML, molecular energy estimation, combinatorial optimization, and Hamiltonian simulation. The evaluation first exposes the bottleneck, then studies baseline sensitivity, scaling behavior, hardware projection, and workload-specific advantage frontiers.

This paper makes the following contributions:

\begin{itemize}[leftmargin=*]
    \item \textbf{End-to-end threshold model.} We define practical quantum supremacy as a same-task, same-quality break-even condition between a native HPC path and a quantum-circuit application path.
    \item \textbf{Logging framework.} We build a pipeline that records runtime breakdowns, quality, circuit metadata, GPU metadata, Slurm metadata, and repeat-timing evidence.
    \item \textbf{Practical workload evidence.} We evaluate controlled quantum ML and a suite covering ML, chemistry, optimization, and simulation, including a 3,552-case large profile, OpenFermion/PySCF chemistry, and sparse Krylov baselines.
    \item \textbf{Scale-out validation.} We run the large profile up to 32 GPU nodes and report weak scaling, fixed-work scaling, bundled allocation behavior, and repeat timing.
    \item \textbf{Hardware-region analysis.} We convert measured circuit costs into required execution speed, shot throughput, and quality-gap recovery, then classify why each workload is hard.
\end{itemize}
