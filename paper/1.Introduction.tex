\section{Introduction}

Quantum computing provides a different way to compute. Unlike classical computers that use binary bits, quantum computers use qubits. Qubits can represent superposition and entanglement, which makes them useful for quantum simulation, optimization, chemistry, and machine learning. These properties motivate many claims of future quantum supremacy.

However, current quantum computers are still limited. They have noise, limited qubit counts, short coherence time, and high access cost. Because of these limits, many quantum applications cannot yet be tested directly on reliable large-scale quantum hardware. As a result, HPC systems and quantum circuit simulators have become the practical platform for studying quantum applications before fault-tolerant quantum hardware is available.

To support this direction, many simulators and frameworks have been developed for HPC systems. Libraries such as \cuQuantum allow users to execute quantum circuits on GPUs, while prior systems such as ScaleQsim and AURORA-Q improve simulation scalability on leadership-scale systems~\cite{scaleqsim,auroraq}. These systems answer an important question: how can we simulate larger quantum circuits faster on HPC?

But this is not the same as quantum supremacy for applications. A simulator can be faster than another simulator, but the quantum-circuit application can still be slower than a native HPC application. For example, a native classifier can train directly on GPU-friendly tensors, while a quantum-circuit classifier must encode data, build circuits, run many circuit evaluations, extract measurements, and run classical postprocessing. Similar gaps appear in chemistry, optimization, and scientific simulation: the quantum part may be promising, but the end-to-end application still includes input preparation, repeated evaluations, error overhead, and classical control. These extra stages can dominate total time.

\noindent\textbf{Observation 1: Simulator speed is not application speed.}
Figure~\ref{fig:intro-gap} shows the comparison target of \SystemName. A circuit simulator is only one component of the quantum path. The full quantum path also includes encoding, circuit generation, repeated evaluations, measurement, optimizer steps, and postprocessing.

\noindent\textbf{Observation 2: Native baselines are strong.}
Native HPC/ML applications already use mature software stacks and hardware-efficient kernels. Therefore, a fair quantum supremacy claim must compare against a native implementation of the same workload, not only against another quantum simulator.

\noindent\textbf{Observation 3: Supremacy is a break-even condition.}
Even if the quantum-circuit path is slower today, it can still be useful if it tells us how fast future quantum hardware must be. Thus, the goal is not only to measure \cuQuantum time. The goal is to invert the measurement and compute the required quantum gate time, shot throughput, and error overhead.

\noindent\textbf{Observation 4: Real applications are diverse.}
Public claims about quantum computing often move from one successful example to broad expectations such as better AI, faster drug discovery, or better optimization. A systems paper cannot validate such claims with one toy workload. It must cover representative application families and show the threshold for each family.

\noindent\textbf{Observation 5: Advantage is a feasible region, not a slogan.}
For a practical workload, quantum advantage depends on several conditions being true at the same time: the quantum path must reach the target quality, the native baseline must be strong, the circuit must fit the available logical qubits, shots must be parallelized enough, and error overhead must not erase the speedup. \SystemName therefore reports an advantage frontier rather than a single yes/no answer.

Many previous studies focus on one part of this stack. Table~\ref{tab:intro-position} summarizes the gap. ScaleQsim and AURORA-Q improve quantum simulation on HPC systems. \cuQuantum provides high-performance GPU primitives. Native ML frameworks provide strong classical baselines. \SystemName connects these pieces into an application-level supremacy threshold model.

\noindent\textbf{Key idea.}
\SystemName treats quantum supremacy as a modeling and analysis problem. In this paper, the supremacy threshold is the condition where the projected quantum-circuit path becomes faster than the measured native HPC and ML path under the same workload and quality target. For each workload, \SystemName records the cost of each stage and then projects the quantum hardware region where this condition holds.

In this paper, we present \SystemName, a quantum supremacy modeling and analysis study for HPC systems. \SystemName starts with a controlled ML workload: \texttt{sklearn digits} native ML baselines, quantum kernel classifiers, and QNN/VQC classifiers. This first workload is the calibration point that validates the measurement pipeline. We then scale the study to a practical suite with ML, molecular energy estimation for drug discovery, combinatorial optimization, and Hamiltonian simulation. This structure follows the logic of our accepted systems papers: first expose the bottleneck, then define the modeling design, then evaluate each component, scaling behavior, and sensitivity.

This paper makes the following contributions:

\begin{itemize}[leftmargin=*]
    \item \textbf{Supremacy threshold definition.} We define quantum supremacy as a break-even condition between native HPC and ML paths and quantum-circuit application paths at the same target quality.
    \item \textbf{Measurement framework.} We build a Perlmutter measurement pipeline that records runtime breakdowns, quality, circuit metadata, GPU metadata, and Slurm allocation information.
    \item \textbf{Practical workload suite.} We evaluate controlled quantum ML and a practical suite covering ML, chemistry, optimization, and simulation, including a 3,552-case large profile and a baseline-coverage gate with OpenFermion and PySCF H$_2$, LiH, and H$_2$O active-space chemistry instances and sparse Krylov simulation baselines.
    \item \textbf{Perlmutter scaling result.} We run the large profile up to 32 GPU nodes and report both weak scaling and fixed-workload strong scaling.
    \item \textbf{Modeling and analysis.} We convert measured circuit costs into required logical gate speed, shot throughput, and quality-gap recovery, then analyze the workload-specific hardware region where supremacy becomes possible.
    \item \textbf{Advantage insights.} We classify workloads by the reason advantage is hard: native-dominated, quality-limited, encoding-limited, shot-limited, or hardware-speed-limited.
\end{itemize}
